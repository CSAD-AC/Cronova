# 调度器系统优化目标文档

## 概述

本文档定义了调度器系统的9项核心优化目标，对标XXL-JOB企业级特性，同时满足业务实际需求。完成全部优化后，系统将具备企业级任务调度平台的核心能力。

---

## 一、业务需求优化项

### 1.1 文件夹上传支持

**作用**：支持用户上传整个目录树到MinIO，而不仅仅是单个文件。适用于需要批量管理脚本资源的场景。

**实现思路**：
1. 前端增加文件夹选择器（`<input type="file" webkitdirectory>`）
2. 前端递归读取文件夹结构，生成文件列表和相对路径
3. 后端Java增加多文件ZIP上传接口，解压后逐个上传到MinIO
4. 或前端直接递归上传，保留目录结构在MinIO中（如`folder/script.py`）
5. 数据库Script表增加`isDirectory`标识，支持目录类型脚本
6. 数据库Script表增加`parentId`字段，用于构建脚本层级关系
7. 前端展示脚本层级关系（如树状图）
8. 后端Java增加`parentId`字段，用于构建脚本层级关系
---

### 1.2 Worker负载均衡

**作用**：根据Worker的实际负载情况智能分配任务，避免部分Worker过载而其他空闲，提升系统整体吞吐量。

**实现思路**：
1. Worker定期上报负载信息（CPU、内存、当前任务数）
2. 调度中心维护Worker负载状态（心跳时更新）
3. 任务分配时选择负载最低的Worker
4. 支持配置Worker权重（高权重Worker分配更多任务）
5. 支持任务亲和性（某些任务只在指定Worker执行）

---

### 1.3 日志上传优化

**作用**：解决当前每次日志追加都下载-合并-上传的低效问题，减少MinIO API调用和延迟。

**实现思路**：
1. Worker本地增加日志缓冲区（如内存或本地文件）
2. 定期（如每秒）或达到阈值（如1KB）时批量上传
3. 使用MinIO的`composeObject`进行增量追加（若支持）
4. 或使用本地滚动日志文件，任务完成后统一上传
5. 增加日志压缩上传选项（gzip）

---

### 1.4 指数退避重试策略

**作用**：任务失败时使用指数退避算法进行重试，避免频繁重试导致系统压力过大。

**实现思路**：
1. 当前固定间隔重试 → 改为指数退避：`delay = baseDelay * (2 ^ retryCount)`
2. 增加最大重试延迟限制（如最多5分钟）
3. 增加抖动（jitter）避免惊群效应：`delay = delay * (0.5 + random())`
4. 支持配置退避参数（基础延迟、最大延迟、抖动开关）
5. 重试时记录每次延迟时间，便于问题排查

---

## 二、对标XXL-JOB企业级特性

### 2.1 阻塞处理策略

**作用**：当任务执行时间超过调度间隔时，决定如何处理新的调度请求。避免任务积压和系统过载。

**实现思路**：
1. Task表增加`blockStrategy`字段
2. 三种策略：
   - `SERIAL_EXECUTION`（串行）：新请求进入FIFO队列，等待前序任务完成
   - `DISCARD_LATER`（丢弃后续）：如果任务正在执行，丢弃新的调度请求
   - `COVER_EARLY`（覆盖之前）：如果任务正在执行，中断当前执行，立即执行新的
3. 调度任务前检查Worker执行状态，根据策略决定是否执行

---

### 2.2 调度过期策略

**作用**：当调度中心因故障等原因错过调度时间时，决定如何处理。

**实现思路**：
1. Task表增加`misfireStrategy`字段
2. 两种策略：
   - `DO_NOTHING`（忽略）：跳过过期的调度，不补偿
   - `FIRE_ONCE_NOW`（立即补偿）：立即触发一次执行
3. CronTaskScheduler记录上次执行时间，检查是否过期
4. 过期时根据策略处理

---

### 2.3 任务依赖（子任务）

**作用**：支持任务A执行完成后自动触发任务B，形成任务依赖链。适用于有先后顺序的工作流。

**实现思路**：
1. Task表增加`parentId`字段（指向父任务ID）
2. 任务执行完成后，检查是否存在子任务
3. 子任务触发条件：父任务执行成功（或任意状态）
4. 支持配置依赖条件（成功/失败/完成）
5. 检测循环依赖（任务A → B → A）
6. 任务执行结果消息中携带父任务ID，便于追踪

---

### 2.4 任务分片

**作用**：将大数据量任务拆分为多个子任务并行执行，充分利用集群能力提升处理速度。

**实现思路**：
1. Task表增加分片配置字段：
   - `shardingTotal`：总分片数
   - `shardingItem`：当前分片序号（0-based）
   - `shardingParam`：分片参数（如数据范围）
2. 调度时根据分片数生成多个TaskRun
3. 脚本接收分片参数，通过环境变量或参数传入
4. 示例：`shardingParam="0-1000"`表示处理ID 0-1000的数据
5. 支持多种分片策略：平均分片、哈希分片、自定义分片

---

### 2.5 调度中心集群HA

**作用**：调度中心支持集群部署，避免单点故障，提高系统可用性。

**实现思路**：
1. 引入Redis分布式锁（基于Redisson）
2. 多调度中心实例竞争锁，锁持有者执行调度
3. 锁超时自动释放，其他实例接管
4. 任务执行记录增加调度中心实例标识
5. 支持Web界面查看当前活跃的调度中心实例

## 六、调度器核心逻辑优化分析

### 6.1 当前调度逻辑架构

调度器核心组件位于 `scheduler-JAVA` 模块，主要包括：

| 组件 | 文件路径 | 功能描述 |
|------|----------|----------|
| CronTaskScheduler | `scheduler-JAVA/src/main/java/com/sjdt/scheduler/task/CronTaskScheduler.java` | 核心调度器，扫描并执行到期的Cron任务 |
| ScheduledTaskRunnerTask | `scheduler-JAVA/src/main/java/com/sjdt/scheduler/task/ScheduledTaskRunnerTask.java` | 定时触发器，每60秒调用一次扫描 |
| TaskTimeoutMonitor | `scheduler-JAVA/src/main/java/com/sjdt/scheduler/task/TaskTimeoutMonitor.java` | 超时监控，每30秒检查超时任务 |
| WorkerServiceImpl | `scheduler-JAVA/src/main/java/com/sjdt/scheduler/service/impl/WorkerServiceImpl.java` | Worker管理，支持标签匹配 |

**当前调度流程**：

```
定时触发 (每60秒) → CronTaskScheduler.scanAndExecuteTasks()
    ├─ 从Redis缓存或数据库获取活跃任务
    ├─ 遍历任务，使用cron-utils判断是否需要执行
    └─ 执行任务
        ├─ script类型 → RocketMQ → Worker执行
        └─ callback类型 → HTTP回调执行器
```

---

### 6.2 现有调度逻辑存在的问题

#### 问题1: 固定60秒扫描间隔，无法满足秒级Cron任务

- **现状**: 扫描间隔固定为60秒
- **问题**: 对于 `* * * * *`（每分钟执行多次）这类高频Cron，完全无法满足
- **代码位置**: `ScheduledTaskRunnerTask.java` 第22行 `@Scheduled(fixedRate = 60000)`

#### 问题2: Cron判断逻辑存在漏执行风险

- **现状**: `shouldExecuteNow` 方法通过 `lastExecution` 和当前时间比较判断
- **问题**: 如果任务在上一次扫描窗口内应该执行但错过了，本次会被忽略
- **代码位置**: `CronTaskScheduler.java` 第144-177行

```java
// 当前判断逻辑
boolean shouldExecute = (nowMillis - lastMillis < 60000) && (nowMillis >= lastMillis);
```

#### 问题3: Worker选择策略过于简单（负载不均）

- **现状**: 标签匹配Worker时，只选择第一个匹配的Worker
- **代码位置**: `TaskServiceImpl.java` 第432-436行

```java
// 当前简单的选择逻辑
com.sjdt.scheduler.domain.po.Worker selectedWorker = matchedWorkers.get(0);
```

- **问题**:
  - 没有考虑Worker当前负载
  - 没有考虑Worker当前执行的任务数量
  - 可能导致某些Worker过载，其他Worker空闲

#### 问题4: 缺乏任务优先级机制

- **现状**: 所有任务平等对待，按扫描顺序执行
- **问题**: 重要任务可能因为排在后面而延迟执行

#### 问题5: 缺乏执行窗口控制

- **现状**: 多个Cron任务可能在同一时刻触发执行
- **问题**: 可能导致资源竞争、数据库连接池耗尽

#### 问题6: 多实例部署存在重复执行风险

- **现状**: 没有分布式锁机制
- **问题**: 如果部署多个Scheduler实例，可能导致任务重复执行

---

### 6.3 详细优化方案

#### 优化1: 动态扫描间隔 + 精确执行时间触发

**目标**: 支持秒级Cron任务精确执行，减少无效扫描

**实现方案**:
1. 记录每个任务的"下一次执行时间"，优先扫描即将到期的任务
2. 使用堆结构（优先队列）管理待执行任务，按执行时间排序
3. 动态调整扫描间隔：空闲时60秒，有任务时缩短到1秒

**技术实现**:
```java
// 使用PriorityQueue按下次执行时间排序
PriorityQueue<TaskExecutionContext> taskQueue = new PriorityQueue<>(
    Comparator.comparing(TaskExecutionContext::getNextExecutionTime)
);

// 动态计算下次扫描间隔
long calculateNextScanInterval(List<Task> tasks) {
    if (tasks.isEmpty()) return 60000L; // 无任务60秒
    LocalDateTime nextExecution = tasks.stream()
        .map(this::calculateNextExecutionTime)
        .min(LocalDateTime::compareTo)
        .orElse(LocalDateTime.now().plusMinutes(1));
    long secondsUntilNext = Duration.between(LocalDateTime.now(), nextExecution).getSeconds();
    return Math.max(1000L, Math.min(secondsUntilNext * 1000, 60000L)); // 1秒~60秒
}
```

---

#### 优化2: 智能Worker选择（负载均衡）

**目标**: 根据Worker实际负载智能分配任务，提升系统整体吞吐量

**实现方案**:
1. 从Redis获取Worker实时状态（当前任务数、CPU使用率等）
2. 选择负载最低的Worker执行任务
3. 综合评分算法：
   - Worker当前正在执行的任务数量（权重: 40%）
   - Worker最近任务完成时间（权重: 30%）
   - Worker标签匹配度（权重: 30%）

**技术实现**:
```java
// 负载评分算法
public double calculateLoadScore(Worker worker, Set<String> requiredTags) {
    int currentTaskCount = getWorkerCurrentTaskCount(worker.getId());
    double cpuUsage = getWorkerCpuUsage(worker.getId());
    double tagMatchScore = calculateTagMatchScore(worker, requiredTags);

    // 分数越高负载越低
    return 0.4 * (1.0 - currentTaskCount / MAX_TASKS_PER_WORKER) +
           0.3 * (1.0 - cpuUsage) +
           0.3 * tagMatchScore;
}

// 选择负载最低的Worker
public Worker selectBestWorker(Set<String> requiredTags) {
    return workers.stream()
        .max(Comparator.comparingDouble(w -> calculateLoadScore(w, requiredTags)))
        .orElse(null);
}
```

#### 优化3: 添加任务优先级机制

**目标**: 支持任务重要性分级，关键业务优先执行

**实现方案**:
1. Task表添加 `priority` 字段（数值越小优先级越高，默认值：5）
2. 调度时按优先级排序
3. 高优先级任务优先获取Worker资源

**数据库变更**:
```sql
ALTER TABLE task ADD COLUMN priority INT DEFAULT 5 COMMENT '任务优先级，数值越小越高';
```

---

#### 优化4: 执行窗口控制（防突刺）

**目标**: 避免同一时刻大量任务执行，保护后端资源

**实现方案**:
1. 配置最大并发执行任务数 `maxConcurrentTasks`（默认：100）
2. 超过阈值时，任务进入等待队列
3. 使用令牌桶算法控制任务发放速率

**技术实现**:
```java
// 令牌桶限流
private final RateLimiter rateLimiter = RateLimiter.create(100); // 每秒100个令牌

public boolean tryAcquire() {
    return rateLimiter.tryAcquire(100, TimeUnit.MILLISECONDS);
}

// 或者使用信号量控制并发
private final Semaphore semaphore = new Semaphore(100);

public void executeWithLimit(Runnable task) {
    semaphore.acquire();
    try {
        task.run();
    } finally {
        semaphore.release();
    }
}
```

---

#### 优化5: 分布式锁防止重复执行

**目标**: 多实例部署安全，避免任务重复执行

**实现方案**:
1. 使用Redis分布式锁（基于Redisson）
2. 每个任务执行前先获取锁
3. 锁超时自动释放（如30秒）

**技术实现**:
```java
@Autowire
private RedissonClient redissonClient;

public void executeWithLock(Task task) {
    String lockKey = "task:lock:" + task.getId() + ":" + LocalDateTime.now().toString();
    RLock lock = redissonClient.getLock(lockKey);

    boolean acquired = lock.tryLock(0, 30, TimeUnit.SECONDS);
    if (acquired) {
        try {
            executeTask(task);
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```
