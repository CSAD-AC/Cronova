## 1. RocketMQ 集群模式下定向任务被非目标 Worker ACK 吞掉（消息静默丢失）

**涉及模块**：调度器（RocketMQ 投递）、Worker 执行器（消费端）
**修复阶段**：阶段二（路由策略 + 定向投递修复）

### 现象

- 定向发给某 Worker 的任务，目标 Worker 的日志里没有处理记录；反而是别的 Worker 出现「定向任务不匹配，跳过处理」。
- RocketMQ 消费进度里该消息显示「已消费」，但**没有任何 Worker 真正执行**。
- 任务运行实例长期 `pending`，直到 120s 派发超时监控触发重试兜底，用户感知为任务迟迟不执行或最终失败。

### 设计演进与根因

任务投递经历了两个阶段：

1. **广播模式（原设计）**：所有 Worker 共享消费组、广播订阅，每条消息所有 Worker 都能收到；定向任务靠消费端软过滤——目标 Worker 处理、其他 Worker 拒绝（`return True`）。
   - 问题：**通用任务（公共任务）会被每个 Worker 各执行一遍**，造成重复执行。通用任务需要"一个任务只被一个 Worker 执行一次"的约束下发。

2. **集群模式（引入 bug）**：为满足通用任务"只执行一次"，任务消费改为集群模式——同组一条消息只投递给**一个**消费者实例。
   - 问题：集群模式下 Broker 把消息**任意**分给组内某个实例（与消息里的 `targetWorkerId` 无关）。当这条定向消息恰好分给非目标 Worker 时，消费端软过滤执行"拒绝"——而"拒绝"的实现是 `return True`（**ACK**）。ACK 意味着该条消息已被消费，Broker 据此推进消费位点 → **消息从全组消费视角消失，定向任务静默丢失**。

**根因链**：
- 集群模式"一消息只投一个消费者"的语义，与"定向投递 + 非目标拒绝"的消费端软过滤**不兼容**：一旦收到，语义上已经消费，消费端没有"替别人拒收"的合法动作。
- 把"跳过"实现成 ACK，等于帮全组把这条消息消费掉。

### 修复方案（阶段二）

把路由权从消费端收归调度侧，改用 Broker 硬定向：

1. **生产端按 WorkerID 打 Tag 定向投递**：`syncSend("TASK_EXECUTE:" + workerId, ...)`（RocketMQ `topic:tag` 语法）。
2. **消费端每 Worker 独立消费组**：`WORKER_EXECUTOR_GROUP_{workerId}`，订阅表达式 = 自己的 workerId。Broker 按 Tag 过滤，不是发给自己的消息根本不会推过来。
3. **删除消费端 `targetWorkerId != 自己 return True` 的软过滤分支**。
4. **无可用 Worker 时 park**：调度侧路由选不出 Worker 就不发消息，run 保持 `pending`，交 120s 派发超时监控兜底。

### 为什么必须"一 Worker 一组"

RocketMQ 要求**同一消费组内所有实例的订阅表达式一致**；若 N 个 Worker 仍共用一组、各自订阅自己的 id，rebalance 时订阅表互相覆盖、行为未定义。改成一 Worker 一组后组内单实例，无 rebalance 问题，Broker 按 Tag 过滤零浪费。

### 修复验证

- 3 个 Worker + 100 条定向任务：100% 由目标 Worker 执行，非目标 Worker 的消费组不再收到该 Tag 的消息。
- 通用任务仍只被一个 Worker 执行（组内单实例天然满足"只执行一次"）。

### 经验教训 / 防再犯

1. **消费端收到消息 = 已经消费**：任何"这条不该我处理"的判断都必须发生在"收到"之前（Broker 侧过滤），而不是收到之后用 ACK 表达拒绝。
2. **"定向投递"是中间件能力，不是消费端职责**：需要按目标选择消费者时，用 Tag + 独立消费组在 Broker 侧解决，不要靠消费端软比较 `targetWorkerId`。
3. **消费模式选型先对语义**：广播（每实例都收到）≠ 集群（同组只投一个）≠ Tag 定向（按订阅过滤）。任务"只执行一次"用集群或定向；控制指令"全体都要收到"才用广播。
4. 遇到"消息消失但日志显示已消费"类问题，优先怀疑 ACK / 消费位点语义，而不是网络或超时。
