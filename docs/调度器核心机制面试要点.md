## 1. Redis 分布式锁

### 1.1 概念与通俗解释

- 分布式锁 = 在"多台机器"之间实现互斥：同一时刻只允许一个节点持有钥匙、执行临界区。
- 类比：只有一个钥匙的洗手间。谁拿到钥匙谁用，用完交还；钥匙上还上了个定时锁，防止拿着钥匙的人晕倒在里面不出来（TTL 兜底）。
- 为什么不用 `synchronized`/`ReentrantLock`：那只是**单 JVM 进程内**的锁。调度器起两个实例 = 两个进程，JVM 锁互相看不见。

### 1.2 常用场景

- 定时任务调度集群：只让一个实例扫描触发。
- 分布式定时任务选主 / 库存扣减 / 幂等领取 / 分布式发号。
- 任何"多个节点抢一个名额"的场景。

### 1.3 具体用法

核心就一条 Redis 命令（原子）：

```
SET lock:scan <token> NX EX 4
# NX：key 不存在才设置成功（抢锁）
# EX：4 秒自动过期（防死锁）
# token：本实例唯一标识（防误删别人的锁）
```

释放必须用 Lua 脚本校验 token 再删（否则会删掉别人的锁）：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else return 0 end
```

配套概念：

- **看门狗续期**（Redisson RLock）：任务没跑完、锁快过期时自动续期，避免"锁到期了活还没干完，另一节点也进来"。
- **公平性**：普通锁非公平，极端场景可考虑公平锁，代价是性能。

### 1.4 本项目实现思路（具体实例）

【现状】全项目 grep 无 `redisson/tryLock/setIfAbsent/SETNX`——**没有任何分布式锁**。`ScheduledTaskRunnerTask` 是 `@Scheduled(fixedRate=60000)` 单实例轮询，所以现在**只能单机部署**，多实例必然重复触发。

【目标】新增 `common/SchedulerLock.java`（对应升级方案 §2.2）：

```java
@Component
public class SchedulerLock {
    private static final String LOCK_KEY = "scheduler:lock:scan";
    private static final String UNLOCK_LUA = """
            if redis.call('get', KEYS[1]) == ARGV[1] then
                return redis.call('del', KEYS[1])
            else return 0 end""";
    private final String token = UUID.randomUUID().toString(); // 实例级标识
    private final RedisTemplate<String, Object> redisTemplate;
    private final DefaultRedisScript<Long> unlockScript;

    public boolean tryLock(Duration ttl) {
        return Boolean.TRUE.equals(
            redisTemplate.opsForValue().setIfAbsent(LOCK_KEY, token, ttl));
    }
    public void unlock() {
        redisTemplate.execute(unlockScript, List.of(LOCK_KEY), token); // Lua 校验防误删
    }
}
```

接入方式（`ScheduledTaskRunnerTask` 60s → 5s）：

```java
@Scheduled(fixedRate = 5000)
public void run() {
    if (!lock.tryLock(Duration.ofSeconds(4))) return;   // 抢到锁的实例才干活
    try { cronTaskScheduler.scanAndTrigger(); } finally { lock.unlock(); }
}
```

**关键设计取舍（面试必答）**：TTL(4s) 略小于扫描周期(5s)——宁可"偶尔双扫"也不能"死锁永久停摆"。因为正确性由下一层的 CAS 兜底，锁只负责**降低竞争、提升吞吐**，不是正确性的唯一来源。

### 1.5 面试深挖点

1. **锁过期了还会重复触发吗？** → 不会。DB 的 CAS（`WHERE next_trigger_time=旧值`）是第二道防线，即使锁全失效双实例同时扫，也只有一个 UPDATE 成功。锁解决吞吐、CAS 解决正确性。
2. **为什么 value 放 token + Lua 释放？** → 防实例 A 锁超时后 B 拿到锁，A 的 finally 又把 B 的锁删掉（误删他人锁）。
3. **为什么不直接用 DB 行锁（`SELECT ... FOR UPDATE`）？** → 可以，xxl-job 就是用 `xxl_job_lock` 行锁。等价地把触发权收敛到一次原子 DB 操作上；本方案选 Redis SETNX 是为减少 DB 压力 + 释放时机更灵活。两者原理相同，要能自洽地讲一种。

## 2. CAS 抢占（乐观锁）

### 2.1 概念与通俗解释

- CAS（Compare-And-Swap，乐观锁）：**更新时不加锁，而是在 UPDATE 的 WHERE 里带上"我看到的旧值"**，数据库原子地判定"值还是旧值 → 更新成功；已被别人改过 → 影响 0 行，放弃或重试"。
- 类比：抢火车票。你手上记着"还剩 1 张"，去更新时带上条件 `WHERE 余票=1`；另一个人刚买完变成 0，你的 UPDATE 影响 0 行，抢票失败。
- "乐观"= 默认没人跟我抢，只在最后一步用原子条件兜底，比全程加锁（悲观锁）开销小。

### 2.2 常用场景

- 库存扣减、余额扣减（经典 `UPDATE ... SET stock=stock-1 WHERE stock>0`）。
- 分布式任务**触发权抢占**（本轮该不该我发）。
- 实体带 `version` 字段的乐观锁更新。
- 状态机流转（pending→running→success 只允许单向）。

### 2.3 具体用法

核心是"检查影响行数"：

```java
int won = taskService.update(new LambdaUpdateWrapper<Task>()
        .eq(Task::getId, task.getId())
        .eq(Task::getNextTriggerTime, firedAt)     // 关键：乐观锁条件 = 我看到的旧值
        .eq(Task::getStatus, TaskStatus.active)
        .set(Task::getNextTriggerTime, next)
        .set(Task::getLastTriggerTime, now));
if (won == 0) return;   // 别的实例已抢先触发 → 直接放弃，绝不重复发
```

SQL 视角就是：

```sql
UPDATE tasks
SET next_trigger_time = ?, last_trigger_time = ?
WHERE id = ? AND next_trigger_time = ? AND status = 'active'
-- 影响行数 = 0 表示被别人抢了，本次触发作废
```

### 2.4 本项目实现思路（具体实例）

【现状】触发判断是 `CronTaskScheduler.shouldExecuteNow` 的"60s 窗口 + 最近一次理论触发点"启发式：**既不记"这一拍已发"，也不带任何旧值条件**，所以同一窗口内第二次扫描/第二个实例会重复发；扫描延迟超 60s 又会静默漏发。结果侧 `TaskResultConsumer` 用 `insertOrUpdate` **无条件覆盖**——正是缺 CAS 的表现（迟到结果覆盖新状态）。

【目标】触发主流程改为"**到期查询 → misfire 判定 → CAS 抢占**"：

```java
private void trigger(Task task, LocalDateTime now) {
    LocalDateTime firedAt = task.getNextTriggerTime();
    LocalDateTime next = nextTriggerTime(task.getCronExpr(), firedAt);

    // misfire：理论触发点已落后超过 5 分钟 → 放弃补跑本拍，直接对齐未来（防雪崩补跑）
    if (firedAt.isBefore(now.minusMinutes(5))) {
        next = nextTriggerTime(task.getCronExpr(), now);
        log.warn("misfire: 任务{}落后{}，跳过补跑对齐至{}", task.getId(), ...);
    }

    int won = taskService.update(/* 上面 2.3 的 CAS，WHERE next_trigger_time=旧值 */);
    if (won == 0) return;   // 别人已触发，放弃

    dispatch(task, now);    // 抢占成功才派发
}
```

**双层防重分工（面试核心话术）**：

- 分布式锁：解决**吞吐**——避免 N 个实例空转竞争、全去查库。
- CAS：解决**正确性**——锁全部失效也只有一个 UPDATE 成功。
- 等价物：xxl-job 用 DB 行锁抢 `xxl_job_lock` 表，本质都是"把触发权收敛到一次原子数据库操作"。

### 2.5 面试深挖点

1. **CAS 和分布式锁什么关系？谁防重复？** → 锁防"并发空转"，CAS 防"实际重复"；锁可以全失效，CAS 不能丢。
2. **CAS 失败怎么办？** → 直接放弃（说明别的实例已处理），不要死循环重试；重试要有上限和退避。
3. **为什么能保证"不重"？** → 同一行的旧值条件只允许一次 UPDATE 成功；"不漏"由 misfire 对齐 + 到期索引扫描兜底（详见机制 11）。
4. **对比悲观锁（FOR UPDATE）** → 悲观锁并发下阻塞排队、开销高；乐观锁适合冲突概率低的读多写少场景，本场景触发冲突极低，乐观锁更合适。

## 3. 幂等性保障

### 3.1 概念与通俗解释

- 幂等 = 同一个操作（用同一个业务标识）**执行 N 次，效果和执行 1 次相同**。
- 为什么必须讲：RocketMQ/Kafka 都是 **at-least-once**（至少一次）语义——消息可能重复投递、可能延迟重投、Worker 宕机重跑。**消息不保证不重复，业务必须自己保证重复无害**。
- 类比：去银行取钱，你的取款请求带了"请求号 9527"。银行收到重复的 9527 请求，只处理一次，后续重复请求直接回"已处理"。

### 3.2 常用场景

- MQ 消费者收到重复消息（重复执行任务）。
- 支付/订单回调（同一订单重复回调）。
- HTTP 客户端超时重试（服务端可能已处理）。
- 定时任务重复触发、失败重试叠加（重试 = 天然更容易重复）。

### 3.3 具体用法（三层手段，从强到弱）

| 手段      | 说明                           | 典型实现                                                        |
| ------- | ---------------------------- | ----------------------------------------------------------- |
| 唯一业务键   | 每条业务记录带全局唯一 ID，DB 主键/唯一索引挡重复 | `taskRunId` 唯一；重复 insert 抛唯一键异常                             |
| 执行权声明   | 执行前抢一个"只此一人"的 token          | Redis `SET key token NX EX`；已存在 → 不执行                       |
| 条件更新状态机 | 更新时校验当前状态，只允许合法迁移            | `UPDATE ... WHERE id=? AND status IN ('pending','running')` |

### 3.4 本项目实现思路（具体实例）

【现状】两条最痛的缺口：

- Worker 执行前**没有任何执行权声明**（`task_service.py`/`python_handler.py` 无 SETNX）→ MQ 重复投递 = 同一任务重复跑。
- 结果侧 `TaskResultConsumer` 用 `insertOrUpdate` **无条件覆盖** → 超时重试换 Worker 后，旧 Worker 迟到的结果会把新状态整个盖掉；DELETE 掉的 run 还会被迟到结果"复活"。

【目标】补齐两层（对应升级方案 §5.3）：

① **Worker 抢占（执行权声明）**——`task_service.py` 执行前：

```python
# SET task:run:claim:{taskRunId} <workerId> NX EX <timeout+60>
# 已存在 → 说明已有人（或已有重复消息）在执行 → 直接 ACK 不执行
claimed = redis.set(f"task:run:claim:{task.taskRunId}",
                    Config.WORKER_ID, nx=True, ex=task.timeoutSeconds + 60)
if not claimed:
    logger.warning("重复消息或已被抢占，跳过执行 taskRunId=%s", task.taskRunId)
    return True
```

② **结果条件更新（状态机）**——`TaskResultConsumer` 把 `insertOrUpdate` 换成：

```sql
UPDATE task_run
SET status = ?, worker_id = ?, end_time = ?, ...
WHERE id = ? AND status IN ('pending','running')
-- 影响 0 行 = 迟到结果（该 run 已终态/已转移）→ 丢弃并 debug 日志
```

**为什么这样就不会重复/不会被污染**：

- MQ 重复投递 → SETNX 挡住第二份执行；
- 超时重试已换新 Worker → 旧 run 已是终态 → 旧 Worker 迟到结果条件更新 0 行被丢弃；
- Worker 假死复活 → 它的迟到结果同样被条件更新拒绝。

**设计决策：超时复用 runId vs 失败新建 runId**（详见机制 4）——历史记录保留靠"新建 run"，防数据膨胀靠"复用 run"。

### 3.5 面试深挖点

1. **at-least-once 下怎么做到 exactly-once？** → 消息层做不到，业务层用幂等收口（唯一键 + 执行权 + 条件更新），讲清楚"靠幂等把 at-least-once 收敛成业务上的 exactly-once"。
2. **SETNX 为什么能防重复执行？** → 抢占是原子的，谁先 SET 成功谁拥有执行权，后来者 NX 失败直接放弃。
3. **幂等放哪一层？** → 消费入口（SETNX）、状态写库（条件更新）、结果回写（唯一键）三层都要，单层挡不住所有路径。
4. **删记录后结果复活怎么防？** → 条件更新只更新存在的行 + `insertOrUpdate` 改为"存在才更新"，禁止结果路径 insert。

## 4. 错误重试机制

### 4.1 概念与通俗解释

- 重试 = 失败后**隔一段时间再执行一次**，直到成功或达到最大次数。
- 关键认知：要区分**可重试错误**（网络抖动、瞬时过载、目标未就绪——重试能解决）与**不可重试错误**（代码 bug、参数错误、依赖缺失——重试只会浪费）。
- 重试和幂等是**孪生兄弟**：只要重试就可能重复，所以重试必须配幂等（机制 3）。

### 4.2 常用场景

- 任务执行失败自动重跑。
- 消息投递失败重投。
- 超时后重新派发（Worker 死了换一个）。
- HTTP 调用 5xx/超时重试（配合退避）。

### 4.3 具体用法

- **固定间隔 / 指数退避 / 最大次数**：`retryCount`、`retryIntervalSeconds` 可配置。
- **RocketMQ 延迟消息**：官方 18 级延迟（1s/5s/10s/30s/1m/2m/.../2h），`syncSend(topic, msg, timeout, delayLevel)`，让消息"到点"才重新可见。
- **兜底监控**：光靠 MQ 重投不够，还要一个扫描器兜漏网（消息丢了、消费端卡死等）。

### 4.4 本项目实现思路（具体实例）

RocketMQ 延迟级别换算（`RocketMQDelayUtil.getDelayLevel(intervalSeconds)`）：

```java
if (delaySeconds > 0) {
    int delayLevel = RocketMQDelayUtil.getDelayLevel(delaySeconds);
    taskProducerService.sendTaskWithDelay(message, delayLevel);   // 到点重投
} else {
    taskProducerService.sendTask(message);
}
```

**两种重试语义（面试重点，本项目现成）**：
| 触发条件 | 处理方式 | 为什么 |
|---|---|---|
| 执行**失败**（exit code≠0） | **新建 run**（新 taskRunId）重发 | 保留历史记录，一次失败一条记录 |
| 执行**超时**（Worker 无心跳/未领用） | **重用当前 runId** 重发 | 防数据膨胀（同一个实例反复重发不产生新记录） |

`TaskTimeoutMonitor` 的双超时监控：

- **派发超时**：pending 超过 120s（无 Worker 领用）→ 超时重试；
- **执行超时**：running 且超过 `timeoutSeconds` 无心跳 → 发 STOP + 超时重试；
- 只要 Worker 正常上报心跳，运行多久都不会被误判超时。

【现状的坑——面试可以主动讲】：

1. **重试双重触发**：`TaskResultConsumer.checkAndTriggerRetry` 对 `timeout` 状态也触发"新建 run"重试，而 `TaskTimeoutMonitor` 对超时是"复用 run"重试 → 同一超时可能两边各重试一次。修复：明确"超时重试只走超时监控（复用 run）"，结果消费者只对 `failed` 触发新建。
2. **超时语义**：现在判"距 lastHeartbeatTime 无心跳时长"，不是"总运行时长"——任务只要一直上报心跳就永不超时，`timeoutSeconds=0` 时 Worker 宕机任务永久悬挂（联系机制 9 的故障转移一起讲）。

### 4.5 面试深挖点

1. **为什么超时重用 runId、失败新建 runId？** → 超时往往同一执行实例还没产出有效结果，重用防止记录爆炸；失败一般已有可区分的原因，新建保留审计。两者都依赖幂等兜底。
2. **重试会不会把下游打爆？** → 用退避 + 最大次数 + 熔断（机制 5）控制；还要防"重试风暴"（一批任务同时失败同时重试）。
3. **MQ 延迟消息为什么比 Thread.sleep 好？** → 不占线程、进程重启不丢（消息在 Broker）、天然支持分布式。
4. **重试和幂等的关系？** → 重试制造重复，幂等吸收重复；没有幂等的重试是危险的。

## 5. 熔断 / 降级 / 限流（保护机制）

### 5.1 概念与通俗解释

- **熔断（Circuit Breaker）**：下游连续失败超过阈值 → 开关**打开**，后续请求直接快速失败（fail-fast）不再打下游，让下游喘息；冷却后放少量探测流量（**半开**），成功则关闸恢复。类比：保险丝，电流过大就熔断，防止烧坏整屋。
- **降级**：主动牺牲非核心能力保核心——返回兜底数据、缓存降级、丢弃低优任务。
- **限流 / 背压**：控制进入系统的速率（令牌桶/漏桶），或让上游感知"我处理不动了"（背压）。消费者处理不过来时，无界排队不是方案，是灾难。

三者关系一句话：**限流挡住"量"，熔断挡住"病"，降级兜住"坏"**。

### 5.2 常用场景

- 调度器调用外部 HTTP 回调、数据库、MQ 下游。
- 回调 URL 对应系统故障时，避免调度器被拖死。
- Worker 执行能力有限时，避免消息无限堆积内存。
- 大批量任务同时失败时，避免重试风暴。

### 5.3 具体用法

熔断状态机三态：`CLOSED(关) → OPEN(开) → HALF_OPEN(半开) → CLOSED`

```text
CLOSED  --连续失败数/错误率超阈值-->  OPEN（快速失败，不调下游）
OPEN    --冷却时间到-->              HALF_OPEN（放少量探测请求）
HALF_OPEN --探测成功-->              CLOSED（恢复）
HALF_OPEN --探测失败-->              OPEN（重新熔断）
```

常用实现：Hystrix / Resilience4j / Sentinel（`@CircuitBreaker`、熔断规则：失败率阈值、最小调用数、滑动窗口、冷却时长）。限流常用 `RateLimiter`（令牌桶）。

### 5.4 本项目实现思路（具体实例）

【现状】**完全没有熔断/限流**，且有两处最需要的地方：

1. **回调任务**：`TaskCallbackExecutor` 在调度器内**同步阻塞**执行 HTTP 回调（`HttpCallbackClient.executeCallback`）。目标 URL 故障 → 每个回调耗到超时 → 调度器扫描线程被拖死 → **整轮调度停摆**。这是最该加熔断的地方。
2. **Worker 端背压**：`python_handler` 用 `ThreadPoolExecutor(max_workers=10)` + **无界队列** → 消息堆积时无限排进内存，Worker 崩溃即丢队列任务。应改有界队列 + 拒绝策略（丢弃并让调度器超时监控重派）。

【目标/改造思路（设计要点，面试回答素材）】：

- **回调熔断**：按 `callback_url`（或业务方）维度维护熔断器——连续 N 次失败/超时 → OPEN（快速失败 + 标记该 run failed + 告警）→ 冷却 30s 后 HALF_OPEN 放 1 条探测 → 成功恢复。
- **调度扫描保护**：扫描 + 派发包在超时/并发上限里，回调改为异步线程池执行（彻底与扫描循环解耦）。
- **Worker 背压**：有界队列 + 饱和时拒绝（reject），拒绝的消息靠 MQ 重投/调度器超时监控接管；可结合 per-worker 并发上限（按 cpu/内存动态算）。
- **降级**：系统内已有雏形——`DISCARD_LATER` 阻塞策略本质就是"负载高时丢弃本轮"（机制 6），可以当降级讲。

### 5.5 面试深挖点

1. **熔断为什么需要半开（HALF_OPEN）状态？** → 否则下游恢复后永远没有探测流量，系统"永远熔断"；半开在 OPEN 和 CLOSED 之间搭了一座桥。
2. **熔断 vs 限流 vs 降级区别？** → 限流挡量、熔断挡病、降级兜坏；可以组合用（先限流，再熔断，最后降级）。
3. **你的系统哪里最需要熔断？** → 回调任务的同步阻塞是最佳回答点（现状就是它拖死整轮扫描）。
4. **为什么不早做？** → 诚实回答"目前单机规模下未触发，但回调同步执行已经是隐患，升级方案里列为必补项"——这比辩解更有力。

## 6. 阻塞策略（触发并发控制）

### 6.1 概念与通俗解释

- 问题：一个 cron 任务上一轮还没跑完，**下一个触发点又到了**——是并发跑、丢弃本轮、还是排队？
- 三种策略对应三种业务偏好（类比会议室：上个人没散会，新人怎么办？赶人 / 这轮不来 / 门口排队）。

### 6.2 常用场景

| 策略                  | 行为                | 适用                  |
| ------------------- | ----------------- | ------------------- |
| `DISCARD_LATER`（默认） | 上一轮没结束 → 本轮**丢弃** | 报表类、幂等重算类（少跑一次无伤大雅） |
| `COVER_EARLY`       | 杀掉上一轮，派新的         | "以最新数据为准"的同步类任务     |
| `SERIAL`            | 排队，等上一轮终态后再跑      | 有顺序依赖的链路任务          |

### 6.3 具体用法（触发时判定，派发前）

```java
TaskRun running = taskRunMapper.selectOne(new LambdaQueryWrapper<TaskRun>()
        .eq(TaskRun::getTaskId, task.getId())
        .in(TaskRun::getStatus, TaskRunStatus.running, TaskRunStatus.pending)
        .orderByDesc(TaskRun::getCreateTime).last("LIMIT 1"));
if (running != null) {
    switch (task.getBlockStrategy()) {
        case DISCARD_LATER -> { logRunSkipped(task); return; }      // 丢弃本轮
        case COVER_EARLY  -> sendTaskControl(stopMsgFor(running));  // 杀旧派新（广播控制 topic）
        case SERIAL       -> createQueuedRun(task);                 // 置 queued，等终态
    }
}
```

`SERIAL` 需要一个推进器：捞 `queued` 状态 run，同 taskId 无 running 兄弟时转 `pending` 派发（`TaskRunStatus` 增加 `queued/skipped`）。

### 6.4 本项目实现思路（具体实例）

【现状】Task 实体里**没有** `block_strategy` 字段，触发时也**不检查**是否已有 running/pending——上一轮没跑完下一轮照发，完全由用户自行负责"别撞车"。

【目标】字段 `block_strategy` 落库（默认 `DISCARD_LATER`）+ 上述触发判定。**面试话术**：这是把"执行并发"的决策权交给任务配置，和 xxl-job 的阻塞处理策略对齐；DISCARD_LATER 作为默认值恰好和熔断/降级呼应（见机制 5）。

### 6.5 面试深挖点

1. **DISCARD_LATER 会不会丢数据？** → 会"丢本轮"，所以适合"结果可重算/可合并"的任务；对不可丢的用 SERIAL。要能讲清楚取舍。
2. **COVER_EARLY 杀旧进程会不会造成数据不一致？** → 靠幂等（机制 3）兜底：旧进程的迟到结果被条件更新拒绝。
3. **SERIAL 队列会不会无限积压？** → 需要排队上限或超时丢弃策略（可延伸到降级）。

## 7. 路由策略（负载均衡）

### 7.1 概念与通俗解释

- 路由 = **调度器主动决定"这个任务发给哪个 Worker"**，而不是把消息丢进 topic 让 MQ 随机分配。
- 为什么要主动：才能真正做到负载均衡、数据亲和（同一数据的主/从任务打同一机器）、故障转移、标签约束。

### 7.2 常用场景

- 多 Worker 间均匀摊派任务。
- 带标签约束的任务只发给具备环境的 Worker（TAG_MATCH）。
- 特定数据/任务稳定打到同一 Worker（CONSISTENT_HASH）。
- Worker 故障时发给健康节点（FAILOVER）。

### 7.3 具体用法（策略 SPI）

```java
public interface RouteStrategy {
    String name();   // 存 tasks.route_strategy
    WorkerSnapshot select(Task task, List<WorkerSnapshot> candidates);
}
```

| 策略              | 核心逻辑                                                            |
| --------------- | --------------------------------------------------------------- |
| ROUND_ROBIN     | Redis `INCR scheduler:route:rr` 取模（多实例共享游标）                     |
| RANDOM          | `ThreadLocalRandom`                                             |
| CONSISTENT_HASH | `TreeMap<Long,Worker>` 虚拟节点×160，`hash(taskId)` 顺时针找最近节点         |
| LEAST_LOAD      | `score = 0.4*cpu + 0.3*mem + 0.3*100*running/maxConcurrent`，取最小 |
| FAILOVER        | 按心跳新鲜度排序，逐个探活（`EXISTS heartbeat` key）选第一个活的                     |
| TAG_MATCH       | 先按标签过滤，再走 LEAST_LOAD；无匹配 → park 告警                              |

一致性哈希要点（必背）：虚拟节点把每个物理节点复制成 160 个虚拟节点散列到环上，**打散热点、减小子集倾斜**；节点扩容/缩容只迁移约 `1/N` 的 key，其余不动。

### 7.4 本项目实现思路（具体实例）

【现状】**没有路由策略**，而且是反面教材：

- 标签匹配后**永远取 `matchedWorkers.get(0)`**（`TaskServiceImpl.publishScriptTask` L450）——第一个匹配的 Worker 恒定承接所有负载（"固定亲和"，比随机还差）；
- `cpuUsage/memUsage/runningTasks` 负载数据采集进了 Redis（`scheduler:worker:info:{id}`）又同步 DB，**但没有任何代码用它做路由决策**；
- cron 触发路径甚至不看标签（机制 1 的问题 7）。

【目标】`WorkerRegistry`（从 Redis 心跳 key + 负载 Hash 组装在线 Worker 快照）+ `RouteStrategy` SPI + `RouteStrategyRouter`（Spring 自动装配 Map<String,RouteStrategy>），任务创建/更新透传 `route_strategy` 字段。**面试话术**：现有"负载数据躺在 Redis 里没人用"是最好的切入点——"数据采集了，但路由决策没接上，我补的就是这一环"。

### 7.5 面试深挖点

1. **一致性哈希解决什么？虚拟节点作用？扩容后怎么迁移？** → 数据倾斜 + 最小迁移；虚拟节点打散热点；扩容只迁 ~1/N，其余不动。
2. **LEAST_LOAD 比 xxl 的 LFU 好在哪？** → LFU 只数触发频次，本方案按 cpu/mem/运行数打分，更贴近真实负载。
3. **负载数据从哪来、多久刷新？** → Worker 心跳 2s 上报 → Redis Hash 实时负载 → 路由时读 Redis（不能读 DB，太慢）。

## 8. 任务分片（并行扩容）

### 8.1 概念与通俗解释

- 分片 = 把一个任务的数据按主键拆成 N 份，**并行**跑 N 个实例，每份只处理自己那段。
- 类比：100 万行数据要清洗，1 个人干 10 小时，10 个人各干 10 万行 → 1 小时。
- 核心不变量：**不重不漏**——每一行恰好属于一片，所有片加起来就是全量。

### 8.2 常用场景

- 大数据量批处理（清洗/同步/报表/导出）。
- 定时任务吞吐不足时横向扩并行度。

### 8.3 具体用法（稳定分区 + 单片重试）

```text
shardTotal 固定（任务上配置，数据分片永不漂移）
片 -> 数据归属：hash(数据主键) % shardTotal == shardIndex
片 -> Worker：shard i 发给 online.get(i % online.size())   // 一台可跑多片
```

关键规则：

- **shardTotal 永不动态变化**：一变则 `hash(数据)%total` 的分区全变，违背不重不漏。
- **单片失败单片重试，重试不换片**（同一段数据只能重跑在同一分区定义下）。
- Worker 上下线只影响"哪台跑哪片"，不影响"数据归哪片"。

### 8.4 本项目实现思路（具体实例）

【目标】`TaskExecuteMessage` 增加 `shardIndex/shardTotal/shardBatchId`，触发时：

```java
String batchId = UUID.randomUUID().toString();
for (int i = 0; i < shardTotal; i++) {
    TaskRun run = createShardRun(task, i, shardTotal, batchId); // task_run 每片一行
    producer.sendTask(messageWithShard(task, i, shardTotal, batchId),
                      online.get(i % online.size()).id());       // Tag 定向投递
}
```

Worker 端向子进程注入分片环境变量（三个 handler 统一处理）：

```python
env["SJDT_SHARD_INDEX"] = str(task.shardIndex)
env["SJDT_SHARD_TOTAL"] = str(task.shardTotal)
env["SJDT_SHARD_BATCH_ID"] = str(task.shardBatchId)
# 脚本侧约定：hash(数据主键) % SJDT_SHARD_TOTAL == SJDT_SHARD_INDEX 的行归本片处理
```

结算：`ShardSettlementService` 在每片结果到达时统计同 `batchId` 的终态片数，**全片终态才结算**（任一片 failed → 批次 failed，否则 success）。**非分片任务即 N=1 特例**（shardIndex=0、shardTotal=1、batchId=runId），走同一条代码路径。

**与 xxl-job 的差异（面试点）**：xxl 用"广播触发，执行器按注册表序号自认分片"；本系统用"N 条 Tag 定向消息"——复用定向投递基础设施，且天然支持**单片失败单片重试**（xxl 广播重试是整体重发）。代价是 N 条消息流量——规模级 tradeoff 要能讲。

### 8.5 面试深挖点

1. **分片某片失败怎么办？怎么保证不漏数据？** → hash 稳定分区（shardTotal 固定）+ 单片独立重试（重试不换片）+ 全片终态才结算。
2. **为什么发 N 条定向消息而不是广播自认分片？** → 复用定向投递 + 单片重试；代价是消息条数，讲 tradeoff。
3. **怎么证明不重不漏？** → 压测：Σ各片行数 == 总行数，两两交集为空；杀 1 片 Worker → 该片重试成功、其他片不受影响。
4. **分片总数大于 Worker 数行不行？** → 行，一台跑多片是常态，还能更均衡。

## 9. 心跳与故障转移（高可用）

### 9.1 概念与通俗解释

- 心跳 = 节点周期性报告"我还活着"。接收方用 **TTL + 超时判定**判断死亡。
- 故障转移 = 一旦判定某个执行节点死亡，把它手上的活**接管**过来（判终态 + 重新派发到健康节点）。
- 类比：群里每 2 秒报一次到；超过 30 秒没报到 → 判定掉线，把他手上的活儿分给别人干。

### 9.2 常用场景

- Worker 宕机后其 running/pending 任务自动转移。
- 调度器多实例互相接管。
- 任何"有状态节点 + 需要自愈"的分布式系统。

### 9.3 具体用法

```text
节点 → 每 2s 写 Redis key（TTL 30s）【活着的证明】
巡检 → 每 10s 检查：key 不存在 = 掉线
转移 → 掉线节点名下 running/pending 的孤儿任务：
      ① 条件更新判终态（failed, reason=worker offline）
      ② 新建 run（不重用旧 runId，不与旧执行权纠缠）
      ③ 重发 → 路由策略重新选在线 Worker
兜底 → 原有超时监控（机制 4）双保险
```

**假死/复活语义（at-least-once）**：旧 Worker 复活后其迟到结果会被"条件更新状态机"拒绝（旧 run 已终态 → 0 行），不会污染新 run；MQ 重复投递由 SETNX 兜底（机制 3）。

### 9.4 本项目实现思路（具体实例）

【现状】心跳链路存在但**故障转移缺失**：

- Worker 2s 心跳 → Redis `scheduler:worker:heartbeat:{id}`（TTL 30s）+ 负载 Hash（`WorkerController.heartbeat`）；
- `WorkerHeartbeatCheckTask` 每 30s 巡检，离线只做三件事：同步最后负载 → 标记 `offline` → 清 `target_worker`；
- **不处理该 Worker 名下 running/pending 的任务**——只能靠 `TaskTimeoutMonitor` 按任务自身无心跳超时被动回收。任务 `timeoutSeconds=0` 时**永久悬挂**。

【目标】存活检测 30s → 10s；离线处理补上主动转移（升级方案 §5.2）：

```java
// ① 离线 Worker 名下 running/pending 孤儿 run → 条件更新判终态
List<TaskRun> orphans = taskRunMapper.selectList(...eq(TaskRun::getWorkerId, offlineWorkerId)
        .in(TaskRun::getStatus, TaskRunStatus.running, TaskRunStatus.pending));
for (TaskRun run : orphans) {
    markFailed(run, "worker offline, failover");  // 条件更新，防与迟到结果竞态
    TaskRun newRun = createRetryRun(run);         // ② 新建 run，沿用任务重试预算
    dispatch(newRun);                             // ③ 重发 → 路由策略选在线 Worker
}
```

### 9.5 面试深挖点

1. **Worker 宕机时它上面 running 的任务怎么办？** → 心跳 TTL 剔除（10s 检测）→ 孤儿 run 判终态 + 新建 run 重路由（秒级生效）+ 无心跳超时监控兜底（双保险）；at-least-once，重复由 SETNX 兜底，迟到结果被条件更新拒绝。
2. **假死（网络分区）复活怎么办？** → 旧 Worker 迟到结果被条件更新拒绝；前提是状态机条件更新做对（机制 3）。
3. **心跳间隔和 TTL 怎么配？** → 间隔 2s / TTL 30s（容忍 ~15 次丢失）；巡检周期要小于 TTL 才能及时判死，10s 巡检 + 30s TTL 合理。

## 10. 消息可靠投递（RocketMQ 语义）

### 10.1 概念与通俗解释

- RocketMQ 默认 **at-least-once**：一条消息至少被投递一次，可能重复。**语义本身不丢不重，业务侧要防重（机制 3）。**
- **集群消费（Clustering）**：同组一条消息只投给组内**一个**消费者实例（负载分摊）。
- **广播消费（Broadcasting）**：同组每个消费者实例**都收到**。
- **Tag 过滤**：Broker 按 Tag 做第一道过滤，消费者订阅 `expression` 只收自己关心的 Tag。

### 10.2 常用场景

- 调度器 → Worker 的任务派发（定向：用 Tag=workerId）。
- Worker → 调度器的结果回流（集群消费）。
- 控制指令（停止/暂停）需要所有 Worker 都收到 → 广播。

### 10.3 具体用法（定向投递的正确姿势）

```java
// 生产端：目的地 "topic:tag"
rocketMQTemplate.syncSend("TASK_EXECUTE:" + workerId, MessageBuilder.withPayload(msg).build(), 3000);
```

```python
# 消费端：每 Worker 独立消费组 + 按自己的 workerId 订阅（Broker 侧过滤）
self.task_consumer = PushConsumer(f"{Config.MQ_CONSUMER_GROUP}_{Config.WORKER_ID}")
self.task_consumer.subscribe(Config.MQ_TASK_TOPIC, self._message_listener,
                             expression=Config.WORKER_ID)   # 别人的消息根本不会推给我
```

### 10.4 本项目实现思路（具体实例）

【现状】**定向丢消息 Bug（本系统最经典的一个坑，必背）**：

- `mq_consumer.py` L87-94：所有 Worker 共用 `WORKER_EXECUTOR_GROUP`、订阅 `expression="*"`（集群模式），非目标 Worker 收到定向任务后 `return True`（ACK）；
- 但集群模式一条消息**只投给组内一个消费者** → 定向消息可能被非目标 Worker 消费并 ACK → **任务静默丢失**，只能靠 120s 派发超时反复兜底重试。

【目标】生产端 Tag 定向 + 每 Worker 独立消费组 + 按 Tag 订阅（上述 10.3 代码）。**为什么必须一 Worker 一组（面试深挖点）**：RocketMQ 要求同组内所有实例订阅表达式一致；若 N 个 Worker 共用一组、各自 `expression=自己id`，rebalance 时订阅表互相覆盖、行为未定义。独立组后：组内单实例无 rebalance 问题，Broker 按 Tag 过滤，非本 Worker 消息只推 offset 不投递（零浪费）。

**控制消息用广播**（`TASK_CONTROL` + `WORKER_EXECUTOR_GROUP_CONTROL` 独立组 + BROADCASTING），Worker 内部按 `targetWorkerId` 自行判断是否执行——这是已就绪的基础设施。

### 10.5 面试深挖点

1. **集群模式下定向任务为什么会丢？怎么修？** → 一条消息只投组内一个消费者 + 消费端"不匹配就 ACK"= 吞掉；改为生产端 Tag 定向 + 独立消费组 + 按 Tag 订阅。
2. **为什么必须一 Worker 一消费组？** → 同组订阅表达式必须一致，混用会 rebalance 冲突；独立组后无 rebalance、Broker 侧过滤零浪费。
3. **为什么选 RocketMQ 不选 Kafka？** → 延迟消息原生支持（重试链路依赖）、Tag 过滤（定向投递依赖）、中文生态；Kafka 延迟消息要自建。
4. **你的派发用 MQ，xxl-job 用 HTTP 直连，为什么？** → xxl 不依赖 MQ 所以直连；本系统 MQ 是核心链路（重试=延迟消息、结果回流=MQ），保留 MQ 换来队列持久化 + 原生重投递 + 削峰，代价是拿不到同步派发 ACK——设计取舍要能讲清。

## 11. 调度防重总纲（不重不漏的四层防线）

### 11.1 一句话

**"不重"靠 CAS + SETNX + 条件更新；"不漏"靠到期索引扫描 + misfire 补偿 + 超时监控兜底。** 消息层 at-least-once，业务层用幂等收口。

### 11.2 四层防线（本项目对应落地）

| 层   | 防什么       | 手段                                        | 本项目落点                                                             |
| --- | --------- | ----------------------------------------- | ----------------------------------------------------------------- |
| 触发层 | 多实例/重复触发  | 分布式锁（吞吐）+ CAS 抢占 `next_trigger_time`（正确性） | `SchedulerLock` + `scanAndTrigger` 的 `WHERE next_trigger_time=旧值` |
| 派发层 | 消息重复消费    | Tag 定向投递 + Worker SETNX 执行权声明             | `TASK_EXECUTE:{workerId}` + `SET task:run:claim:{runId} ... NX`   |
| 结算层 | 迟到/重复结果污染 | 条件更新状态机（只允许合法迁移）                          | `UPDATE ... WHERE id=? AND status IN ('pending','running')`       |
| 兜底层 | 漏触发/漏执行   | misfire 对齐 + 双超时监控 + Worker 离线转移          | `firedAt` 落后 5min 对齐未来；120s 派发超时 + 无心跳超时；孤儿 run 重路由               |

### 11.3 面试总述（30 秒版本）

> "我的系统在四个层面保证不重不漏：触发侧用 Redis 锁降竞争、DB CAS 抢触发权，保证同一触发点只有一个实例发出消息；派发侧用 Tag 定向 + Worker 端 SETNX 声明执行权，保证重复消息不会重复跑；结算侧用条件更新状态机，让迟到的旧结果无法覆盖新状态；兜底侧用到期索引扫描 + misfire 对齐防漏触发，用双超时监控 + 离线转移防执行悬挂。整体是 at-least-once 语义 + 幂等收口。"

### 11.4 面试深挖点

1. **任务量涨 100 倍哪里先瓶颈？** → 扫描锁串行（→ 按任务 hash 分桶多把锁分片扫描）；`task_run` 写热点（→ 批量/异步落库）。能答出"先想清楚哪层先顶不住"很重要。
2. **为什么用 DB `next_trigger_time` 而不是纯内存时间轮？** → 内存时间轮重启丢任务；Redis ZSet 跨实例共享 + 可恢复，但 5s 扫描 + 索引在万级任务内已秒级，ZSet 收益 < 复杂度——"明确不做的取舍"本身是加分项。
3. **哪一层错了会出什么事故？** → 触发层错 = 重复/漏执行；派发层错 = 重复执行/静默丢任务；结算层错 = 状态被污染；兜底层错 = 悬挂无自愈。层层有明确的事故模式，这是"分层防重"的价值所在。

## 附：速记 Q&A（每个机制一题）

1. **Redis 分布式锁**：锁过期了会重复触发吗？→ 不会，CAS 是第二道防线。
2. **CAS 抢占**：CAS 失败怎么办？→ 放弃（别人已处理），绝不重复发。
3. **幂等性保障**：at-least-once 怎么做成业务上的 exactly-once？→ SETNX 执行权 + 条件更新状态机收口。
4. **错误重试**：为什么超时重用 runId、失败新建 runId？→ 防膨胀 vs 留审计，都靠幂等兜底。
5. **熔断/降级/限流**：熔断为什么需要半开？→ 给下游恢复留探测通道。
6. **阻塞策略**：DISCARD_LATER 丢本轮真的没问题？→ 适合可重算/可合并任务，不可丢的用 SERIAL。
7. **路由策略**：一致性哈希扩容为什么只迁 ~1/N？→ 环上相邻迁移，虚拟节点打散热点。
8. **任务分片**：单片失败怎么办？→ 单片重试不换片，全片终态才结算，hash 分区永不漂移。
9. **心跳与故障转移**：Worker 宕机任务悬挂？→ 孤儿 run 判终态 + 新建 run 重路由 + 双超时兜底。
10. **消息可靠投递**：定向任务为什么之前会丢？→ 集群消费一条消息只投一个 + 消费端不匹配也 ACK。
11. **调度防重总纲**：不重不漏怎么保证？→ CAS + SETNX + 条件更新防重；索引扫描 + misfire + 超时监控防漏。
