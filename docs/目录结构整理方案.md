# 项目目录结构整理方案

> 目标：让仓库从"根目录散落 + 模块内部不一致"收敛为"根目录干净、文档统一、命名一致"，
> 且**每一类整理独立成 commit，互不干扰**，随时可回滚。
>
> 现状问题速览：
> - 根目录混有 4 个一次性测试脚本、1 个独立实验工程（test2）、1 个草稿目录（test1）、
>   1 个脚手架残留（.github/modernize）、1 个命名含糊的 `model/`
> - 文档分散在 `docs/`、`scheduler-JAVA/docs/`（空）、`scheduler-JAVA/dev-start.txt`、
>   `model/*/*.md`、`Vue/MINIO_INTEGRATION.md` 多处
> - Java 包名大小写不一致：`Interceptor`、`saToken` 与其余全小写包混排
> - SQL 三份脚本职责/命名不清晰（scheduler.sql 与 init 疑似重叠）
> - 本地配置 `local_config.json`、`docker/.env` 被纳入版本控制

## 四、Java 包名大小写统一（Commit C：机械重构，独立提交）

现状：`com.sjdt.scheduler` 下同时存在 `Interceptor`（帕斯卡）、`saToken`（驼峰）与全小写包。

- 目标：全部小写 → `interceptor`、`satoken`
- 操作：改目录名 + 全量替换 `import com.sjdt.scheduler.Interceptor.` → `interceptor.`（IDEA 重构或脚本可机械完成）
- 风险：`saToken` 类名本身保留（`SaTokenInterceptor` 等类名不动），只动包名
- **建议单独 commit**：一旦混入其他改动，回滚困难

## 五、SQL 脚本规约（Commit D）

现状：`scheduler.sql`（416 行，疑似旧全量）、`sjdt-task-engine-init.sql`（238 行，当前基线）、`upgrade_phase1_ha.sql`（阶段一增量）。

```

├── upgrade/
│   ├── upgrade_phase1_ha.sql   # 阶段增量（既有文件移入）
```

## 七、执行节奏与建议

1. **按 Commit A→E 分五步执行**，每步独立、可回滚；A/B 零代码风险，C 机械重构，D/E 需要先核对数据再动。
2. **先做 A+B**（立竿见影、无风险），C 单独安排，D 需先跑一遍 SQL 比对，E 涉及运行配置需确认后再改。
3. 每步完成后 `git status` 核对：**只出现该步预期文件**，防止误伤。
4. 整理后仓库根目录只剩：`README.md`、`.gitignore`、`docs/`、`scheduler-JAVA/`、`sjdt_worker/`、`Vue/`、`examples/`、`experiments/`（可选）。

## 八、建议保留 / 谨慎处理

- `scheduler-JAVA` 与 `sjdt_worker` 模块名：虽是历史命名，但已贯穿文档/路径/部署脚本，**本轮不改名**（成本高、收益低）。
- `model/` 改名 `examples/` 涉及 `model/` 下 3 个 `.md` 引用：改名与文档移动在 Commit A/B 中一并处理，避免引到旧路径。
- `scripts_tmp/` 改名的前提是确认无硬编码路径引用，否则保持现状并在注释中说明用途。
